# Phase 5 — Configuration, cleanup and usability

Branch: `refinement/phase-5-cleanup`, based on Phase 4. No production deployment.

Restaurant identity, public contact details, links, promotions and booking policy now have one validated configuration model. Staff saves pass through authorized server APIs with conflict versions for general settings; malformed timezones, minutes, links, hours and closure dates are rejected. Firebase clients cannot bypass these writes. Credentials and notification recipients remain server environment variables. Existing unknown legacy settings are preserved rather than destructively migrated; inspect them before production to ensure the public general document contains no historical secrets. This is preparation for tenancy, not tenant isolation. Static SEO metadata uses the centralized default identity; dynamic page content uses live configuration.

Public pages subscribe to policy and identity changes. Open status uses business-local time, custom ranges and combined closures, independently of booking lead time. Date-only closures remain literal calendar dates. Special Dates uses accessible add/edit/delete dialogs, validated server actions and explicit load/save errors. Public booking initializes its business-local calendar once and freezes the server-accepted receipt, so live timezone changes cannot overwrite a selected or submitted day. A component regression test covers timezone changes and settings refresh. Public booking uses a focus-managed dialog, labels and autocomplete, busy-state guards, stable idempotency keys and pending-request copy. Menu highlights show real menu data rather than simulated orders or table counts. Menu images use responsive Next Image with safe placeholders. Reduced-motion and keyboard-focus styles are present; accidental white-input/global CSS overrides were removed.

Private guest preferences and seating requests have explicit staff fields and conflict versions. Guest summaries show last completed visit and average known completed party size; unknown imported party sizes are excluded from the average. Staff notes/preferences remain absent from guest responses. Catering inquiries now validate an allowlist, return the saved request independently of delivery, deduplicate retries and persist per-recipient notification jobs in the shared worker. Inquiry messages never imply an accepted event.

Inventory and team models/data subscriptions, live booking policy, menu images and shared magnetic buttons are extracted by domain. Unmounted legacy reservation/menu/reminder components and unused libraries were removed after import tracing. One Tailwind configuration and one middleware remain. The middleware is beside `src/app`, as required by Next.js; HTTP checks cover anonymous/forged-cookie access and the historical middleware-header bypass. The old Express entrypoint has an explicit retirement error; package scripts and Vercel use Next.js. Unknown external manual users of that entrypoint require review before release.

Public pages/assets have explicit caching, while staff, APIs and token-bearing management pages are private/no-store. Management pages also use no-referrer. Font assets are served locally by Next; menu highlights load on demand. Root no-cache metadata and timestamp build IDs are removed. Before/after build JavaScript measurements are recorded in release readiness; these are bundle measurements, not browser speed or Lighthouse scores.

Next 15.5.27, Nodemailer 10.1.0, PostCSS 8.5.29 and gRPC 1.14.6 are pinned/overridden with a regenerated reproducible lockfile. A clean `npm ci` passed. Runtime dependency audit reports zero vulnerabilities. Full audit still reports 16 findings in development tooling (2 moderate, 14 high); an ESLint/Tailwind major migration is separate work, and was not forced into this cleanup.

Final validation: clean typecheck/lint (zero warnings), 63 tests (no skips/TODO), optimized staging production build, API/database/outage smoke, configuration/catering smoke, HTTP cache/auth smoke and persistent capture smoke passed. Mobile booking/receipt, settings, closures, menu and keyboard dialog checks passed; the receipt remained unchanged through a live timezone change/restore. The home first-load bundle decreased from 337 to 324 kB; menu/catering increased modestly, recorded in release readiness.

Validation and release limits are maintained in [release-readiness.md](release-readiness.md). Staging rules alone were deployed. Provider messages and OTPs were captured, all fixtures are synthetic, and no production records were read or changed.

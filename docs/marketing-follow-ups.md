# Marketing follow-ups

Open **Guest Engagement → Marketing follow-ups** (`/admin/marketing`). The queue is calculated automatically from current history when opened or refreshed. It never sends automatically: staff review an individual email or select up to 50 customers, review all recipient-specific previews, then choose **Approve & send**. Closing the review keeps it pending. Dismiss removes that follow-up for the current inactive period.

Reservation and catering eligibility are separate, grouped by trimmed, lowercase email. Customers become eligible strictly after 30 restaurant calendar days (day 31), using the configured business timezone. Reservations use the latest pending/confirmed/seated/completed reservation date. Catering reads the current private staff workflow stage and uses the latest completed event date; a pending inquiry alone does not count as a catered event. Any same-day or future non-cancelled booking/inquiry in that category excludes the customer. Invalid historical dates require review and exclude that customer. No-shows, declined/cancelled records, and test records do not qualify. Recorded `marketingOptOut: true` also excludes the email.

One email is allowed per customer, category, and latest activity date. An approval or dismissal remains in history, preventing repeated monthly messages when a customer does not return. A newer qualifying activity date can produce a new follow-up after another 30 days. Reservation and catering follow-ups can both be eligible for the same person; each requires separate approval.

Approval transactionally rechecks current history and global unsubscribes, checks that the message still matches the reviewed preview, records the staff session ID and exact message, then creates a durable notification outbox job. Repeated requests do not create duplicate jobs. A stale selection rejects the entire batch so staff can refresh. Delivery rechecks eligibility and suppression again; a returned or unsubscribed customer is superseded. Approvals are not scheduled campaigns: they begin delivery after approval, using the existing capture-aware transport. Pending jobs and provider failures use the existing notification worker, lease, backoff, and five-attempt limit. History distinguishes captures from provider acceptance. Provider acceptance is not proof of inbox delivery. SMTP's existing duplicate-on-crash limitation applies.

Emails include the restaurant address, a reservation/catering link, and a signed unsubscribe link. GET opens a confirmation page without unsubscribing (safe for email-link scanners). POST confirms it, and the List-Unsubscribe header points to the separate signed one-click POST endpoint. Existing mailing-list and campaign opt-outs are respected. A new follow-up unsubscribe also updates the shared mailing preference and invalidates old confirmation proofs. Unsubscribes suppress both marketing categories, including pending approved emails; transactional booking messages continue. The signature uses ADMIN_SESSION_SECRET. Changing that secret invalidates older unsubscribe links as well as sessions; preserve it across routine deployments.

Configuration: server Firebase access, `ADMIN_SESSION_SECRET`, `NEXT_PUBLIC_BASE_URL`, `EMAIL_USER`/`EMAIL_PASS` and the existing SMTP settings. General settings must include a valid restaurant timezone. Use capture mode for testing. The authenticated notification worker must run to recover interrupted sends. Full histories are scanned for correctness; if data volume outgrows this approach, introduce transactionally maintained customer activity aggregates before adding pagination to the history reads (a truncated history can hide a newer booking).

Deployment is intentionally pending. Deploy app code and Firestore rules together: marketingCampaigns and marketingSuppressions are server-only, even for client SDK staff sessions. No existing customers are contacted by opening the queue or deploying this feature.
